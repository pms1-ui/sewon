세원 ↔ PLM 의존성 분석

세원 개발이 PLM의 선행조건인가? · 문서·코드 교차 검증 · 최종 정리 2026-11-06

결론 — 세원 완료는 PLM "전체"의 선행조건이 아니다 (병행 과제)

PLM은 세원 연동을 포트+어댑터로 추상화하고 mock으로 전부 구현해, 세원 없이도 백엔드(작업 1~22)·프론트(작업 23) 대부분을 완성했다. 다만 PLM을 실제 업무에 투입하려면(상품 등록·수정, 차수별 입고, 원가·판매실적 연결) 세원 개발이 핵심 선행조건이다. 즉 세원은 "개발의 블로커"가 아니라 "실투입·실데이터 검증의 선행조건"이다.

① 세원 규격 확정→ ② PLM 연동부 개발→ ③ 세원 납품 후 실데이터 검증

세원 납품 전에도 진행할 작업이 있고, 반대로 세원이 끝나도 자동 해결되지 않는 문제(상태 의미 차이·차수 연결 등)가 별도로 존재한다.

1. 왜 세원 의존도가 높은가

PLM의 입력과 결과 확인이 모두 세원을 거치기 때문이다. PLM이 세원에 자동 등록하는 API 방식은 요구사항에서 제외되어 있어, 세원의 엑셀 등록·수정 기능이 제대로 동작해야 PLM에서 작성한 정보가 실제 상품·발주 업무로 연결된다.

PLM에서 작성·수정 → 엑셀 내보내기 → 사용자가 세원에 업로드 → 세원 데이터 수신 → PLM에서 반영 결과 확인

근거: requirements.md Req29 "Childy_PLM은 세원 업로드용 표준 엑셀을 내보내는 역할을 하며, 세원에 직접 자동 등록(API push)하지 않는다."

3. 문서·코드 대조에서 발견한 핵심 문제

1 상품 수정 규칙이 아직 PLM 개발 기준으로 쓰기 어렵다

3차 요청서는 재업로드 시 기존 상품 수정을 요구하면서, 동시에 진행 상태별 수정 불가 필드·수불 발생 이후 제한 필드·필수 전환 필드 목록을 세원에 요청하고 있다. 이 목록을 받아야 PLM도 수정 버튼·검증 규칙을 정확히 만들 수 있다.

수정 키도 불일치: 요청서는 품번+차수+색상코드+사이즈구분+사이즈(5요소)인데 견적/요약은 품번+차수+색상+사이즈로 축약돼 있어, 단순 요약인지 실제 처리 기준 차이인지 확인 필요.

현재 PLM 내보내기는 76필드 CSV 기반이며, 최신 요청의 진행구분·사후원가 세부 필드·헤더 변경을 모두 반영한 최종본은 아니다. 최종 양식 확정과 실제 업로드 검증이 남아 있다.

2 상태 구조 — PLM이 세원을 "베끼지 않고 자체 운전"하도록 정리됨 ◐ 설계로 해소

PLM은 세원 상태를 그대로 받아쓰지 않는다. 상태 운전대는 PLM이 쥔다:

  • 생산 중 전환 = 세원 "진행중"과 무관하게, 공장 확약(포털/전자서명/이메일)이 완료되면 PLM이 자체 전환
  • 입고 중·입고 완료 전환 = 세원이 입고 흐름으로 자동 전환한다(진행중=ERP 입고 등록→WMS 전송 시, 입고완료=WMS 입고 확정→ERP 전송 시, 세원 확정). PLM은 세원 ORDER_STATUS를 주기적으로 pull해서 발주 상태를 그 값으로 동기화한다(세원이 바꾼 상태를 받아 맞춤). 한편 ERP 입고현황의 차수별 입고 수량은 입고 상태(부분입고) 표시·금액/원가 분석 용도이며 발주 상태를 결정하지 않는다(3번 참조)

핵심은 두 시스템의 단계 구분이 다르다는 점이다. 세원은 입고 중심(발주확정 → 진행중=입고시작 → 입고완료)이라 "생산 중" 개념이 없고, PLM은 생산~판매 중심이라 세원에 없는 생산 중·발매 완료·종료가 더 있다. 그래서 세원 상태를 글자 그대로 매핑하면 어긋난다.

나아가 상태 축을 "차수별 발주/생산 6단계" 중심으로 단일화했다(입고 중·입고 완료는 입고 수량으로 자동 전환). 품번 1개에 차수(리오더)별 발주가 여러 개 걸리므로:

  • 상품 수명주기(기획/진행/판매중) = 그 품번의 차수별 발주 상태에서 파생(계산). 사람이 따로 전환하지 않음
  • 입고 상태(미입고/부분입고/입고완료) = 입고 수량에서 자동 계산되는 파생값
  • 종료만 사람이 켜는 플래그(세원 "종료=품번종결"과 동형)

→ 손으로 관리하는 상태를 하나로 줄여, "상품은 판매중인데 발주는 생산중" 같은 모순을 원천 차단.

3 발주 상태는 세원 ORDER_STATUS pull로 동기화, 차수별 입고 수량·금액 분석은 ERP 입고현황으로

PLM은 한 품번에 여러 차수(리오더)의 발주를 관리한다. 그래서 입고가 들어오면 어느 차수 발주에 몇 개가 들어왔는지를 알아야 한다. 그런데 WMS 필드표(27필드)에는 생산 발주번호·리오더 차수가 없다. 반면 ERP 입고현황에는 차수(BATCH_NO)와 차수별 입고 수량·입고일자·시점 원가가 들어 있다.

또한 ERP는 입고를 잡는 순간(입고/반품등록) 수량·시점·원가가 ERP에 다 기록된다. 발주/생산 상태(입고 중·입고 완료)는 세원 ORDER_STATUS를 주기적으로 pull해서 동기화하고, 차수별 입고 수량·금액·원가 분석은 ERP 입고현황으로 한다(WMS는 차수가 없어 발주 연결이 안 됨). WMS는 전사 재고·출고·반품 실물 확인용으로만 병행한다.

→ 발주 상태는 세원 ORDER_STATUS pull로 동기화, 차수별 입고 수량·금액 분석 소스는 ERP 입고현황(차수 포함)으로 확정. 남은 확인: ERP 입고현황 VIEW의 차수·입고일자·수량 컬럼 실제 제공 여부(세원 납품 시 검증).

4 '세원 API만 연결하면 끝'인 상태가 아니다

세원 제공 방식은 DB의 VIEW TABLE이다. PLM 쪽에서 이를 조회·적재하고 내부 API로 공급하는 부분이 필요하다. 실제 VIEW 이름, 컬럼명·자료형, 한 행의 단위, 고유키, 변경·삭제 식별 방식, 샘플 데이터가 있어야 연결부를 확정할 수 있다.

PLM 작업목록상 프론트는 아직 브라우저 내 메모리 데이터로 동작하고 REST 서버 연결은 후속 작업이다. 라인시트·작지·계획 등 일부 서버 경로도 미연결. 또한 동기화 로직에서 PLM이 수정한 상품명이 세원 예전 상품명으로 덮이는 문제를 메모리 데이터로 재현했다(설계는 PLM 수정본 보존이 목표). 이 보완은 지금 진행 가능.

4. 개발 범위 정정 사항

9번(발주번호 채번)·10번(라인시트 양식 변경)은 정리 문서(04 md)에는 "3차 10개 항목"으로 들어가 있으나, 실제 3차 요청서 PDF는 8-2 매장 조회 목록에서 끝나고, 견적에도 두 작업이 별도 항목으로 명시돼 있지 않다. 따라서 현재 파일만으로는 두 항목이 최신 전달·합의 범위에 포함됐다고 볼 수 없다. (단, 엑셀 신규 필드 추가·필드명 변경 자체는 견적에 포함.)
